# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использован датасет `S12-hw-dataset.csv` с ежечасными данными (4320 записей)
- Прогнозировалось следующее значение временного ряда (горизонт 1)
- Выполнен корректный temporal split: train (70%), validation (15%), test (15%)
- Сравнены подходы:
  - **B1 (naive-last)**: прогноз = последнее наблюдённое значение (lag_1)
  - **B2 (moving-average)**: прогноз = среднее за последние 7 наблюдений
  - **B3 (ridge-lag-features)**: Ridge-регрессия на лаговых, rolling и календарных признаках
  - **R1 (gru-forecast)**: GRU с окном 24 часа (сутки)
- Лучшим подходом по validation оказался **B3 (Ridge)** (MAE=3.55)
- На test лучший результат также показал B3 (Ridge) (MAE=3.32)

## 3. Данные и постановка задачи

- **Датасет**: `S12-hw-dataset.csv`
- **Целевая колонка**: target
- **Частота временного ряда**: почасовая (24 наблюдения в день)
- **Горизонт прогноза**: 1 шаг
- **Размер датасета**: 4320 записей
- **Диапазон дат**: 2025-01-01 00:00:00 → 2025-06-29 23:00:00
- **Есть ли дополнительные внешние признаки**: нет
- **Комментарий**: ряд имеет ярко выраженную суточную сезонность (дневные пики, ночные спады) и недельную сезонность (выходные ниже). Присутствуют выбросы. Данные стабильны, тренд слабо выражен.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- train: 2025-01-01 → 2025-05-06 (3024 записи, 70%)
- validation: 2025-05-07 → 2025-06-02 (648 записей, 15%)
- test: 2025-06-03 → 2025-06-29 (648 записей, 15%)
- random split некорректен, так как нарушает временной порядок: модель может "подглядывать" в будущее, что не соответствует реальному сценарию прогнозирования

### 4.2. Признаки для baseline-моделей

- **Лаги**: 1, 7, 14 (суток) — по требованию задания
- **Rolling-признаки**: mean и std для окна 7
- **Календарные признаки**: dayofweek, month, hour, синус/косинус кодирование
- **Пропуски**: удалены после построения признаков
- **Масштабирование**: StandardScaler, обученный только на train (для B3 и R1)

## 5. Модели и эксперименты (B1, B2, B3, R1)

- **B1 (naive-last)**: прогноз = последнее наблюдённое значение (lag_1)
- **B2 (moving-average)**: прогноз = скользящее среднее за 7 предыдущих часов
- **B3 (ridge-lag-features)**: Ridge-регрессия (alpha=1.0) на 14 признаках
- **R1 (gru-forecast)**: GRU с 2 слоями, hidden_size=64, dropout=0.2, окно 24 часа

**Дополнительно:**
- Основная метрика выбора лучшей модели: MAE (на validation)
- Дополнительные метрики: RMSE, MAPE
- window_size для GRU: 24
- Batch size: 32
- Максимальное число эпох: 50
- Optimizer: Adam
- Learning rate: 0.001
- Лучшая модель сохранялась по val_MAE

## 7. Анализ

1. **Наивный baseline (B1)** показал MAE=5.43 — это ожидаемый результат, так как он не учитывает сезонность.

2. **Moving average (B2)** показал худший результат (MAE=9.44), так как усреднение сглаживает полезные сезонные колебания.

3. **Ridge (B3)** значительно улучшил качество (MAE=3.55) благодаря:
   - Лагам 1, 7, 14, улавливающим суточную и недельную сезонность
   - Календарным признакам (час, день недели)
   - Rolling-статистикам, сглаживающим шум

4. **GRU (R1)** показала результат (test_MAE=3.67), близкий к Ridge, но не превзошла его. Причины: малый объём данных и хорошо структурированная сезонность.

5. **Тренд и сезонность** в данных хорошо различимы: суточные колебания (пики днем, спады ночью) и недельный цикл.

6. **Потенциальные утечки данных** исключены: все признаки построены только по прошлому, масштабирование обучено только на train.

7. **Выбор по validation принципиален**: test используется только для финальной оценки.

8. **Наиболее показательные ошибки** GRU приходятся на резкие выбросы.

## 8. Итоговый вывод

- **Какой подход взять как базовый**: Ridge с признаками — прост, интерпретируем, требует меньше ресурсов и показал лучший результат.
- **Когда достаточно простого baseline**: когда данные имеют чёткую сезонность и не требуют учёта долгосрочных зависимостей.
- **Когда переходить к GRU**: когда данных много (>10⁴), есть сложные нелинейные зависимости.
- **Главное про валидацию временных рядов**: temporal split критически важен для получения реалистичной оценки качества.
