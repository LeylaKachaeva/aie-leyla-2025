# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использован датасет `S12-hw-dataset.csv` с ежечасными данными (4320 записей)
- Прогнозировалось следующее значение временного ряда (горизонт 1)
- Выполнен корректный temporal split: train (70%), validation (15%), test (15%)
- Сравнены подходы:
  - **B1 (naive-last)**: прогноз = последнее наблюдённое значение (lag_1)
  - **B2 (moving-average)**: прогноз = среднее за последние 7 наблюдений
  - **B3 (ridge-lag-features)**: Ridge-регрессия на лаговых, rolling и календарных признаках
  - **R1 (gru-forecast)**: GRU с окном 24 часа (сутки)
- Лучшим подходом по validation оказался **B3 (Ridge)** (MAE=3.55)
- На test лучший результат также показал B3 (Ridge) (MAE=3.32)

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: target
- Частота временного ряда: ежечасная (24 наблюдения в день)
- Горизонт прогноза: 1 шаг
- Размер датасета: 4320 записей
- Диапазон дат: 2025-01-01 00:00:00 → 2025-06-29 23:00:00
- Есть ли дополнительные внешние признаки: нет
- Комментарий: ряд имеет ярко выраженную суточную сезонность (дневные пики, ночные спады) и недельную сезонность (выходные ниже). Присутствуют выбросы. Данные стабильны, тренд слабо выражен.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- train: 2025-01-01 → 2025-05-06 (3024 записи, 70%)
- validation: 2025-05-07 → 2025-06-02 (648 записей, 15%)
- test: 2025-06-03 → 2025-06-29 (648 записей, 15%)
- random split некорректен, так как нарушает временной порядок: модель может "подглядывать" в будущее, что не соответствует реальному сценарию прогнозирования

### 4.2. Признаки для baseline-моделей

- Лаги: 1, 7, 14 (суток) — по требованию задания
- Rolling-признаки: mean и std для окна 7
- Календарные признаки: dayofweek, month, hour, синус/косинус кодирование
- Пропуски: удалены после построения признаков
- Масштабирование: StandardScaler, обученный только на train (для B3 и R1)

## 5. Модели и эксперименты (B1, B2, B3, R1)

- **B1 (naive-last)**: прогноз = последнее наблюдённое значение (lag_1)
- **B2 (moving-average)**: прогноз = скользящее среднее за 7 предыдущих часов
- **B3 (ridge-lag-features)**: Ridge-регрессия (alpha=1.0) на 14 признаках
- **R1 (gru-forecast)**: GRU с 2 слоями, hidden_size=64, dropout=0.2, окно 24 часа

Дополнительно:
- Основная метрика выбора лучшей модели: MAE (на validation)
- Дополнительные метрики: RMSE, MAPE
- window_size для GRU: 24
- Batch size: 32
- Максимальное число эпох: 50
- Optimizer: Adam
- Learning rate: 0.001
- Лучшая модель сохранялась по val_MAE

## 7. Анализ

Наивный baseline B1 (lag_1) показал MAE=5.43 — это ожидаемый результат, так как он не учитывает сезонность.

Moving average B2 (окно 7) показал худший результат (MAE=9.44), так как усреднение сглаживает полезные сезонные колебания.

Ridge-регрессия B3 на лаговых и rolling-признаках показала отличные результаты (MAE=3.55 на val и 3.32 на test). Ключевые факторы успеха:
- Лаги 7 и 14 хорошо улавливают недельную сезонность
- Календарные признаки (час, день недели) добавляют информацию о типичных паттернах
- Rolling-статистики сглаживают шум, не теряя сезонность

GRU (R1) на валидации показала MAE=3.87, на тесте — 3.67. Результат близок к Ridge, но не превосходит его. Причины:
- Малый объём данных (~3000 точек после построения окон) — для GRU желательно больше
- Ряд имеет линейную структуру, которую Ridge уже хорошо описывает
- GRU чувствительна к выбросам

Тренд в данных слабо выражен, сезонность — сильная и регулярная. Это делает задачу подходящей для моделей с явными сезонными признаками (лаги, календарь).

Потенциальные утечки данных: использование future-значений при построении rolling-статистик (center=True) или масштабирование на всём датасете до split. В работе все признаки построены только по прошлому.

Выбор по validation, а не по test, принципиален: если бы мы выбирали по тесту, результат был бы нечестным.

Наиболее показательные ошибки GRU приходятся на резкие выбросы, что характерно для рекуррентных сетей на ограниченных данных.

## 8. Итоговый вывод

Для этого датасета лучшим базовым подходом является **B3 (Ridge-регрессия на лаговых и rolling-признаках)**. Она показала наилучшее качество как на валидации (MAE=3.55), так и на тесте (MAE=3.32).

Простые baseline (B1, B2) недостаточно учитывают сложную сезонность ряда.

GRU (R1) имеет смысл переходить, когда:
- объём данных значительно больше (> 10⁴ точек)
- зависимость нелинейная и сложная
- есть необходимость улавливать долгосрочные зависимости

Главное, что я понял про корректную валидацию временных рядов:
- нужно строго соблюдать хронологический порядок
- нельзя использовать future-признаки
- метрики на test считать только один раз после выбора модели по validation
- даже если нейросеть лучше на валидации, на тесте она может проиграть простой линейной модели
